# Contributing to EffectTrace

Thank you for your interest. EffectTrace records evidence-graded relationships
between actions on Kubernetes and what was observed after them. Contributions
that make those relationships more correct, more honest about uncertainty, or
easier to use are very welcome.

By participating you agree to the [Code of Conduct](CODE_OF_CONDUCT.md).
Report security issues privately as described in [SECURITY.md](SECURITY.md),
never in public issues.

## Ways to contribute

- **Report a bug.** Include `effecttrace doctor` output, the graph JSON
  (`effecttrace export`) or, better, a minimal collector recording that
  reproduces the problem with `effecttrace replay`. Remove real identities.
- **Report a wrong attribution.** Say which edge is wrong, its `rule` and
  `facts`, and what ground truth you expected. Wrong `ATTRIBUTED` claims are
  treated as high-priority bugs.
- **Improve documentation**, especially [limitations](docs/limitations.md) and
  [troubleshooting](docs/troubleshooting.md).
- **Add tests or experiments** for situations that are not covered yet.
- **Work on the [roadmap](ROADMAP.md).** Please open an issue first for
  anything larger than a small fix.

## Development workflow

See [docs/development.md](docs/development.md) for the full guide.

```sh
make build
make verify          # fmt, vet, lint, unit + integration tests, scan
make fuzz            # optional, for parser changes
make demo-up && make test-e2e   # for correlation, source or lab changes
```

## Pull requests

1. Fork the repository and create a topic branch.
2. Keep each pull request focused on one change. Describe what it changes and
   why, and link the issue.
3. Add or update tests. Changes to attribution rules need a unit test in
   `internal/correlate` and, when cluster behaviour matters, an experiment.
4. Update documentation in the same pull request, including the
   [evidence model](docs/evidence-model.md) for rule changes,
   [semantic conventions](docs/semantic-conventions.md) for attributes, the
   [JSON Schema](schemas/effect-graph.schema.json) for graph changes, and
   [CHANGELOG.md](CHANGELOG.md) under `[Unreleased]`.
5. Significant design changes need an [ADR](docs/adr/README.md).
6. `make verify` must pass. CI runs the same targets.

### Commits

- Sign off every commit to certify the
  [Developer Certificate of Origin](https://developercertificate.org/):
  `git commit -s`.
- Write commit messages in the imperative mood with a short summary line.
- Do not commit generated binaries, kubeconfigs, recordings or local lab files
  (`.lab/` is ignored).
- Do not hand-edit measured numbers. `docs/results.md`, `docs/benchmarks.md`
  and the README results block are generated by `make test-results` from
  `test-results/*.json`.

The maintainer merges pull requests with signed commits; see
[releasing](docs/releasing.md#signing-policy).

## Design principles to keep

- Every edge has exactly one evidence class, fixed by its relationship.
- Timing alone never becomes attribution.
- When more than one action could explain a change, report an ambiguity.
- Missing data reduces coverage; it is never guessed around.
- Collect the minimum data needed; drop payloads at the source.
- EffectTrace observes. It never mutates the cluster and is not an
  authorization system.
